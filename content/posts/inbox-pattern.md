In the [previous blog](https://priyankchheda.github.io/posts/transactional-outbox-pattern/), the order service started writing `OrderCreated` events to an outbox table instead of publishing directly to the broker, so an order and its event always commit together. That solved losing events. It didn't solve something else: the inventory service, on the receiving end, can now get the same event more than once.

That's not a bug in the outbox. It's the trade-off we made on purpose — a relay that crashes after publishing but before marking a row as sent will publish that row again on restart. Same thing happens on the broker side: if the inventory service processes an event but crashes before acknowledging it — or, on a log-based broker, before its offset commits — the broker redelivers it. Nobody did anything wrong; the message just got sent twice.

So the question shifts from "how do I not lose this event" to "how do I not reserve inventory twice for the same order."

## Why "just make it idempotent" isn't always enough

The advice you'll hear is: make your handler idempotent. And where you can, do it. If handling `OrderCreated` is a `SET reserved = 2 WHERE product_id = 'prod_789'`, running it twice is harmless — same result either way.

But a lot of real handlers aren't naturally idempotent:

```python
def handle_order_created(event):
    for item in event.items:
        db.execute(
            "UPDATE inventory SET reserved = reserved + %s WHERE product_id = %s",
            item.quantity, item.product_id,
        )
```

That's an increment per line item. Run it once, you reserve 2 units of a product. Run it twice, you reserve 4. The second delivery isn't a no-op, it's a bug that silently locks up stock nobody actually asked for.

You can't always redesign the operation into something naturally idempotent, and even if you're careful, mistakes happen. What you actually need is a way to recognize "I've already handled this exact event" and skip it — regardless of what the handler itself does.

## The fix: an inbox table

The idea mirrors the outbox, just on the other side of the wire. The inventory service keeps a table of every event ID it has already processed:

```sql
CREATE TABLE inbox (
    event_id UUID PRIMARY KEY,
    producer VARCHAR(100),
    processed_at TIMESTAMP DEFAULT NOW()
);
```

Before doing any real work, check whether the event ID is already there:

```python
def handle_order_created(event):
    already_seen = db.execute(
        "SELECT 1 FROM inbox WHERE event_id = %s", event.event_id
    )
    if already_seen:
        return  # duplicate, already handled

    db.begin_transaction()
    db.execute(
        "INSERT INTO inbox (event_id, producer) VALUES (%s, %s)",
        event.event_id, "order-service",
    )
    for item in event.items:
        db.execute(
            "UPDATE inventory SET reserved = reserved + %s WHERE product_id = %s",
            item.quantity, item.product_id,
        )
    db.commit_transaction()
```

Two things make this actually work, not just look like it works.

First, the event needs a **unique ID**, generated by the producer, that travels with the event. Without one, a redelivered event and a genuinely new event with the same payload look identical — you can't tell "same order, sent twice" from "different order, same quantity." That ID is what the inbox table keys on.

Second — and this is the part people get wrong — the inbox insert and the inventory update happen **in the same database transaction**. If they were separate, you could insert the inbox row, then crash before updating inventory, and now the event is marked as handled forever even though it never actually did anything. Tying them together means either both happen or neither does, so a crash mid-handler just leaves the event unprocessed and safe to retry.

One more detail: if you have multiple producers, event IDs from different services could collide. In that case, make `producer` part of the key — a composite `UNIQUE (event_id, producer)` — rather than trusting `event_id` alone to be globally unique.

## Insert before you acknowledge

There's a subtlety in *when* you insert into the inbox relative to acknowledging the broker. Do the insert — and the processing — **before** sending the ACK, not after.

Here's why that ordering matters. Suppose you process the event — including the inbox insert — and then ACK the broker, and the ACK itself gets lost on the network. The broker, having never received confirmation, redelivers the same message. Your inbox check runs again, finds the `event_id` already sitting there from the first attempt, and returns before touching inventory a second time. If you'd ACK'd first and inserted after, you'd have no record yet when the redelivery arrives, and you'd process it a second time.

That `SELECT` check handles this sequential case, but it isn't airtight on its own: if two deliveries of the same event are handled at the same instant — say, by two consumer instances — both can pass the `SELECT` before either has committed an `INSERT`. That's what the unique constraint on `event_id` is actually for. One `INSERT` succeeds, the other fails the constraint, and a handler built for production would catch that failure and treat it exactly like an `already_seen` hit rather than letting it surface as an error.

You can't fix any of this by acknowledging the ACK, either — that just moves the same problem one layer up. At some point you have to have a durable record that survives the crash, and that record is the inbox row, written in the same transaction as the work it's guarding.

## What about crashes after the ACK but before the work finishes?

Handling the event and committing might not be a single instant — say the handler also needs to call a third-party shipping API. If the process crashes midway, you're stuck with an event that's neither fully done nor safe to silently drop.

The usual fix is a status column:

```sql
ALTER TABLE inbox ADD COLUMN status VARCHAR(20) DEFAULT 'pending';
```

Insert the row as `pending` when the event arrives. Once the handler finishes its work, flip it to `processed` in the same transaction as the business update. If the process dies in between, the row just sits there as `pending`, and a recovery job can pick it up and reprocess it after a restart or timeout.

That works cleanly when reprocessing means "just redo the local update." It gets murkier when the handler calls out to something external — you don't want to double-charge a card or double-call a shipping API just because you're replaying a `pending` event. That's a case-by-case problem outside what the inbox table itself can solve; the table just tells you *what* needs revisiting, not how to safely redo it.

## What not to do: bolt the event ID onto the business row

A shortcut you'll see is skipping the inbox table entirely and just storing the last-seen event ID directly on the entity it affects — an `last_event_id` column on the inventory row, say. Resist this. It mixes infrastructure concerns (deduplication) into your business schema, and it quietly breaks down the moment a handler touches more than one row or more than one table. The inbox table keeps deduplication as its own concern, separate from whatever the handler actually does.

## If you're on Kafka instead of a queue

Everything above assumes a broker where the consumer decides, per message, whether it's been seen. Log-based brokers like Kafka work a bit differently — they track a **consumer offset**, and everything before that offset is considered handled.

The failure mode is the same shape though: you process a message, then crash before the offset commits, and Kafka replays from the old offset. The fix is the same idea, just cheaper to store — instead of a row per event, you only need to persist the **offset** itself alongside your business update, in the same transaction. Kafka Connect is one way to wire that up if you don't want to manage it by hand.

## Don't lean on "exactly-once" broker features

Kafka has `exactly_once_v2`, RabbitMQ has a deduplication plugin, NATS JetStream and Pulsar have their own answers to this. They're worth using where they fit, but almost all of them come with restrictions — specific client libraries, specific configurations, specific failure modes they don't cover — and none of them let you stop thinking about duplicates entirely.

The safer default is to treat at-least-once delivery as the baseline you're always designing for, and put the dedup logic somewhere you control — an inbox table you can inspect, query, and reason about — rather than trusting it's fully handled two layers down in the broker.

## Putting both halves together

Outbox guarantees an event gets created exactly when the transaction that triggered it commits. Inbox guarantees that no matter how many times that event shows up on the other end, it only gets *acted on* once. Neither one alone gives you a fully consistent system — outbox without inbox just moves the duplicate problem downstream, and inbox without outbox is deduplicating events that might not have been reliably sent in the first place. Together, they're how you get reliable, eventually-consistent behavior across two services without ever reaching for a distributed transaction.
